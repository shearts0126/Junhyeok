## 1. PRE-FLIGHT 결과 — 왜 BLOCKED 였나

T06-1 PRE-FLIGHT 판정은 `BLOCKED — DESIGN RECOVERY REQUIRED` 였다.
결정적 사유 세 가지:

1. **완료조건을 authoritative schema 로 달성할 수 없었다.** backlog 완료조건은
   `적용기간 중첩 차단`(`07:93`) / `중첩 INSERT 실패`(`07v2:196`)인데, `docs/03` 이
   제시한 UNIQUE 2종은 **동일 시작일 중복만** 막고 interval overlap 은 통과시킨다(§20).
2. **Warehouse 의존 컬럼 2개 + Attachment 의존 컬럼 1개가 구현 불가**였다.
   T06-1 의 선행조건은 `T03-1` 뿐이라 T08 을 끌어올 수 없고, `Attachment` 는
   backlog 에 배정된 Task 조차 없다.
3. **T06-3 "승인" 을 표현할 schema 가 없었다.** `approvedBy` UUID 하나로 승인
   상태를 표현하는 것인지, self-approval 정책이 `작성자≠승인자`(v0.1)인지
   `allow_self_approval_sku`(v0.2)인지 문서가 충돌한다.

여기에 effective period 경계 semantics · `supplierType`/`status` 계약 · CHECK 범위 ·
actor FK action 이 모두 미결이라, 구현자가 발명하지 않고는 진행할 수 없었다.

## 7. D-4 — lead time

```prisma
Supplier.defaultLeadTimeDays Int?
SupplierSku.leadTimeDays     Int?
```

**정확한 semantics** (§00 G-03):

| 값 | 의미 |
|---|---|
| `null` | **미입력/미확정** (실측 383행 중 381행) |
| `0` | **명시적으로 0일** — 즉시납 |
| 음수 | 금지 |

★ `null` 과 `0` 은 **다른 값**이다. G-03 은 "null 을 0 으로 대체 금지" 이지
"0 입력 금지" 가 아니므로 **0 을 막지 않는다.**
⛔ DB default 0 금지 (default 자체를 두지 않는다).

```sql
supplier_default_lead_time_days_check
  CHECK (default_lead_time_days IS NULL OR default_lead_time_days >= 0)

supplier_sku_lead_time_days_check
  CHECK (lead_time_days IS NULL OR lead_time_days >= 0)
```

폴백 체인

```text
supplierSku.leadTimeDays ?? supplier.defaultLeadTimeDays ?? null
```

은 **T06-2 에서 구현**한다. T06-1 에서는 구현하지 않는다.

## 16. D-11 — 적용기간 semantics

`SupplierSku` 와 `SupplierSkuPrice` 의 기간은 둘 다 **half-open interval** 이다.

```text
[effectiveFrom, effectiveTo)
```

| 항목 | 의미 |
|---|---|
| `effectiveFrom` | 적용 시작일 — **포함** |
| `effectiveTo` | 적용 종료 경계일 — **미포함** |
| `effectiveTo IS NULL` | 무기한 / open-ended |

따라서

```text
2026-01-01 ~ 2026-02-01
2026-02-01 ~ 2026-03-01
```

은 **서로 중첩되지 않는다.** 같은 날 이전 조건 종료 + 새 조건 시작이 허용된다.

```sql
supplier_sku_effective_period_check
supplier_sku_price_effective_period_check
  CHECK (effective_to IS NULL OR effective_to > effective_from)
```

★ `>=` 가 아니라 `>` 다 — `from = to` 는 **길이 0 구간**이라 아무 날도 포함하지 않는
무의미한 행이므로 금지한다.

## 18. D-14 — overlap DB enforcement

⛔ application validation 만으로 처리하지 않는다. **DB 레벨에서 막는다.**
(완료조건이 "중첩 INSERT 실패" 이므로 DB 가 거부해야 한다.)

```sql
ALTER TABLE supplier_sku
  ADD CONSTRAINT supplier_sku_effective_period_excl
  EXCLUDE USING gist (
    supplier_id WITH =,
    sku_id WITH =,
    daterange(effective_from, effective_to, '[)') WITH &&
  );
```

- `effectiveTo = NULL` 은 daterange 의 **unbounded upper bound** 로 처리된다.
- 이 하나로 DB 에서 전부 차단된다:
  **부분 중첩 · 완전 포함 · open-ended 중첩 · 동일 시작일**
- **경계 접촉(`~02-01` 과 `02-01~`)은 허용**된다 — `'[)'` 이기 때문이다.

Prisma 가 EXCLUDE 를 표현하지 못하므로 **migration raw SQL** 로 추가한다.

⚠️ BOM 의 EXCLUDE(`03:295`)를 그대로 복사하지 않았다 — 그쪽은
`WHERE status='ACTIVE'` predicate 가 있고 supplier 에는 대응 개념이 없다.

```text
@@unique([supplierId, skuId, effectiveFrom])
```

도 **유지한다.** EXCLUDE 가 있다고 삭제하지 않는다.

역할이 중복되어 보여도 **surviving source 보존**을 위해 유지한다.

## 20. btree_gist

T06-1 에서 이 프로젝트 **최초로 `btree_gist` 를 도입**한다.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;
```

uuid 등가비교(`WITH =`)를 daterange 중첩(`WITH &&`)과 하나의 GiST 인덱스에 함께
넣어야 하므로 필수다. ⛔ application fallback 으로 대체하지 않는다.

⚠️ **`prisma migrate diff` 는 EXCLUDE·extension·partial index 를 관찰하지 못한다.**
raw SQL 을 빼먹어도 drift gate 는 통과한다 → **DB integration test 의 `pg_catalog`
검증이 authoritative gate** 다. CI PostgreSQL 에서도 실제 migration 을 적용해 검증한다.

## 21. D-13 — SupplierSkuPrice 는 EXCLUDE 대상이 아니다

⛔ `SupplierSkuPrice` 에 EXCLUDE 를 적용하지 않는다.

가격이력의 authoritative 계약은 공급조건과 **다르다**. `05:103` 원문:

> 적용일 **중복** 차단 / 이전 가격 `effectiveTo` **자동 마감**

즉 겹침은 ① 동일 `effectiveFrom` UNIQUE 와 ② 등록 트랜잭션의 자동 마감으로 막는다.

따라서 T06-1 에서는 기존

```text
@@unique([supplierSkuId, effectiveFrom])
```

만 유지하고, **다른 `effectiveFrom` 을 가진 가격 행의 interval overlap 을 DB EXCLUDE 로
차단하지 않는다.** 여기서 EXCLUDE 를 걸면 아직 존재하지 않는 T06-3 계약을 DB 가
선점하게 된다.

이전 가격 자동 마감은 **T06-3 application transaction** 에서 구현한다.

→ T06-1 완료조건의 "기간 중첩 차단" 은 **SupplierSku 공급조건에 적용**한다.

## 22. SupplierSkuPrice indexes

기존 source 그대로 유지한다.

```text
UNIQUE(supplierSkuId, effectiveFrom)
```

## 23. D-15 — isPrimary invariant

`docs/03` §고유조건 원문을 **그대로 채택**한다.

```sql
CREATE UNIQUE INDEX ux_supplier_sku_primary_current
  ON supplier_sku(sku_id)
  WHERE is_primary = true
    AND effective_to IS NULL;
```

의미: **현재 미종료 SupplierSku 중 SKU 당 대표 1개.**

- ★ key 가 `sku_id` **단독**이므로 공급업체가 달라도 두 번째 현행 대표는 불가능하다.
- ★ 종료된 historical primary 는 새 primary 를 막지 않는다.
  (`ux_external_mapping_primary` 는 predicate 에 `effective_to` 가 없어 **정반대**로
  동작하고, `ux_barcode_primary` 는 `status='ACTIVE'` 조건이다 — **복사하지 말 것**.)
- ⛔ 원 source 가 `effective_from <= today` 를 요구하지 않으므로 추가하지 않는다.

⚠️ **수용된 한계**: 시작일이 미래여도 `effective_to IS NULL` 이면 이 UNIQUE 대상이다.
따라서 "예약 대표(scheduled primary)" 를 만들 수 없다. 그 기능이 필요해지면
**별도 Recovery** 로 다룬다. DB 테스트가 이 한계를 명시적으로 고정한다(#41).

## 29. D-20 — FK contract

T06-1 에서 **실제로 생성하는** FK 5개:

| FK | onDelete | onUpdate |
|---|---|---|
| `SupplierSku.supplierId → Supplier` | **RESTRICT** | CASCADE |
| `SupplierSku.skuId → Sku` | **RESTRICT** | CASCADE |
| `SupplierSkuPrice.supplierSkuId → SupplierSku` | **RESTRICT** | CASCADE |
| `SupplierSkuPrice.createdBy → User` | **RESTRICT** | CASCADE |
| `SupplierSkuPrice.approvedBy → User` | **RESTRICT** | CASCADE |

⛔ **CASCADE DELETE 금지.** 가격 이력을 부모 삭제에 따라 물리삭제하지 않는다.

### actor 가 SET NULL 이 아닌 이유

`Sku.createdBy/updatedBy/approvedBy` 는 SET NULL 이지만 가격이력은 **RESTRICT** 다.

1. 가격이력은 감사 대상이다(`02:337`).
2. **`approvedBy` 의 null 여부가 승인 상태 자체**다(§26).
3. 따라서 사용자 삭제로 SET NULL 되면 **승인된 가격이 미승인으로 뒤집힌다.**

Prisma relation name 은 명시한다: `SupplierSkuPriceCreatedBy` /
`SupplierSkuPriceApprovedBy`. `User` 에는 Prisma compile 에 필요한 **최소 inverse** 만
추가하고 새 business semantics 를 부여하지 않는다.

## 46. D-15·D-16 — SupplierSku PATCH = temporal versioning

`PATCH /api/supplier-skus/{id}` 는 **business term 을 제자리에서 덮어쓰는 API 가
아니다.** 공급조건은 effective-dated history 이며 **두 mode 만** 허용한다.

### mode A — 종료 (body 정확히 `{effectiveTo}`)

- `effectiveTo > existing.effectiveFrom` (아니면 422 `EFFECTIVE_PERIOD_INVALID`)
- open-ended → 종료 가능 / 기존 종료일 **앞당기기** 가능
- ⛔ 기존 종료일 **연장 금지**(422 `VERSION_DATE_INVALID`) ·
  ⛔ `effectiveTo: null` reopen 금지(DTO 400)
- 같은 값이면 실질 변화 없음 — 200 현재 행 / DB write 0 / Audit 0
- 기존 row UPDATE 1건 · 응답 200 updated view · Audit `UPDATE` 1건

### mode B — 새 버전 (body 에 `effectiveFrom` 필수)

`effectiveFrom` 은 기존 row 의 시작일 변경이 아니라 **후속 version 의 시작일**이다.

경계: `newFrom > existing.effectiveFrom` · (finite 면) `newFrom <
existing.effectiveTo` — 위반 시 422 `VERSION_DATE_INVALID`.

트랜잭션(단일, 중간 commit 금지 — **이 순서 필수**):

```text
① target row lock (SELECT … FOR UPDATE)
② 기존 effectiveTo 원본 보관
③ 기존 row effectiveTo = newFrom 로 close      ← 먼저
④ successor INSERT                              ← 나중
   - supplierId·skuId = 기존 값 (identity 불변)
   - supplied field = 새 값 / omitted = 기존 값 복사
   - successor effectiveTo = 명시값 ∥ 기존 row 의 원래 effectiveTo 상속
⑤ Audit: 기존 UPDATE + 신규 CREATE (정확히 2건)
⑥ response = successor view
```

★ new-first 금지 이유: old row 가 열려 있는 동안 EXCLUDE overlap 과 현행 대표
partial UNIQUE 가 자기충돌한다.

- version 에서 변경 가능: supplierSkuCode · supplierSkuName · supplyType · moq ·
  orderMultiple · leadTimeDays · purchaseUom · currency · isPrimary · effectiveTo.
- ⛔ identity(`supplierId`·`skuId`) 변경 금지(400) · 기존 row 의 원래
  `effectiveFrom` 수정 금지.
- `effectiveFrom` 만 보내고 실질 변경이 없으면 400 — 단 successor `effectiveTo`
  변경은 실질 변경이다.

### D-16 — historical/future edit

과거·현재·미래 **모든 row 에 같은 temporal rule** — 직접 business field 수정
금지(400). 정정은 version mode 로만. 유일한 예외는 mode A 의 종료/단축이다.
과거 공급조건을 조용히 덮어쓰는 경로가 없다.

### 동시성

target row 를 `FOR UPDATE` 로 잠근다 — 같은 row 의 동시 versioning 은 직렬화되고
lost update 가 없다. EXCLUDE·partial UNIQUE 는 언제나 최종 방어선이다.
⛔ Route→Prisma 직접 접근 금지 — repository/application 경유.

## 60. 핵심 Recovery 원칙 — 가격 **등록**과 가격 **발효**의 분리

POST price 는 **미승인 가격 제안행을 생성할 뿐**이다. 신규 row 는 항상
`approvedBy = null · createdBy = actor.userId · effectiveTo = null` 이며, POST
순간에는 기존 승인 가격 `effectiveTo` 변경 금지 · 승인 chain 변경 금지 ·
operational asOf 결과 변경 금지다 — predecessor/successor 조회조차 하지 않는다.
가격이 실제 operational price chain 에 들어가는 시점은 **APPROVE 트랜잭션뿐**
이고, 기존 승인 가격 auto-close 와 target `effectiveTo` 계산은 거기서만 한다.

pending 가격은 승인 전까지: 기존 승인 가격을 닫지 않고 · predecessor/successor
를 바꾸지 않고 · asOf operational price 에 포함되지 않는다. 예: 승인
`2026-01-01 ~ NULL` + 신규 pending `2026-08-01` 상태에서 asOf `2026-09-01` 은
계속 기존 승인 가격이다. 신규가 승인된 순간에만 `2026-01-01 ~ 2026-08-01` /
`2026-08-01 ~ NULL` 로 전환한다.

## 64. D-12~D-14 — approved price chain algorithm

target 의 `effectiveFrom = T` 라 할 때, 같은 supplierSkuId 의 **승인된
가격만** 대상으로 (pending 은 제외, target 자신도 pending 이므로 제외):

```text
predecessor: approvedBy IS NOT NULL AND effectiveFrom < T
             ORDER BY effectiveFrom DESC, id DESC LIMIT 1
successor:   approvedBy IS NOT NULL AND effectiveFrom > T
             ORDER BY effectiveFrom ASC,  id ASC  LIMIT 1

if predecessor exists: predecessor.effectiveTo = T
target.effectiveTo = successor ? successor.effectiveFrom : null
target.approvedBy  = actor.userId
```

- predecessor close 는 **실제 값이 변한 경우에만** write + Audit UPDATE.
- **D-12 historical insertion 허용** — append-only 로 제한하지 않는다.
  P1(01-01~12-01)·P3(12-01~NULL) 사이에 P2(06-01) 승인 시
  P1(~06-01)/P2(06-01~12-01)/P3(12-01~NULL) 이 된다.
- **D-24 future 선승인 허용** — 8월에 10-01 가격을 승인해도 기존.effectiveTo =
  10-01, 신규 null. asOf 09-30 은 기존, 10-01 은 신규다.

## 72. D-32 — approve locking · concurrency

## 73. §42 — AuditLog

- **create**: `entityType = SupplierSkuPrice`, `action = CREATE`, before=null,
