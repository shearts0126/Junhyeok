# 2. Posting Service — 동일 재고키 합산 검증

## 2.1 결함 확인

지적하신 내용이 **정확하다.** v0.1 §8.12 의사코드는 다음과 같았다.

```typescript
for (const e of entries) {
  const before = locked.find(byStockKey(e))?.quantity ?? ZERO;   // ← 잠금 시점 스냅샷
  const after  = before.plus(e.quantityDelta);
  if (after.lessThan(0)) { /* 음수 판정 */ }
}
```

`before`를 **잠금 시점 스냅샷에서 매번 읽으므로**, 동일 재고키의 모든 entry가 같은 기준값으로 검증된다.

```
현재고 10
entry 1: K, −6  → 10 − 6 = 4  ✅ 통과
entry 2: K, −6  → 10 − 6 = 4  ✅ 통과   ← 잘못된 기준
balance 갱신(entry별 UPDATE): 10 − 6 − 6 = −2  ❌
```

balance는 `quantity = quantity + delta`를 누적하므로 **최종 수량은 정확히 −2**가 되지만, **검증이 이를 잡아내지 못해 음수재고 차단(P6)이 구조적으로 우회된다.**

이런 입력은 실제로 발생한다 — 엑셀 업로드에서 같은 SKU·창고·LOT 행이 여러 줄인 경우, 세트 해체에서 동일 구성품이 여러 라인인 경우, 3PL 출고 실적이 채널별로 분할된 경우.

## 2.2 수정 내용 (지시하신 7단계 전부 반영)

| # | 지시 | 반영 |
|---|---|---|
| 1 | 정규화된 entries를 재고키별 그룹화 | `04 §8.12` `groupByStockKey()` — 정규화 **후** 그룹화 (순서 중요) |
| 2 | 재고키별 `netQuantityDelta` 합산 | `04 §8.1` `StockKeyGroup` 인터페이스 |
| 3 | 잠금 대상 재고키 중복 제거 | `04 §8.7` — `groups.map(g => g.key)` 는 이미 유일 |
| 4 | 음수 검증을 `현재수량 + netQuantityDelta` 기준으로 | `04 §8.6`, `§8.12` 검증 ⑭ |
| 5 | 원장행은 원본 entries 그대로 저장 | `04 §8.12` ⑯ — `lineNo` 원본 순서 보존 |
| 6 | balance는 재고키별 합산값으로 1회 갱신 | `04 §8.7`, `§8.12` ⑰ |
| 7 | 음수·양수 혼재도 최종 합산값으로 검증 | `04 §8.6` 검증 사례 표 |

## 2.3 파생 변경 (지시에 없었으나 필요한 것)

| 변경 | 사유 |
|---|---|
| **상태전이 검증을 그룹 net 부호 기준으로 전환** (`04 §8.4`) | v0.1은 "음수 delta = from, 양수 delta = to"로 **entry를 짝지었다.** 동일 상태 버킷이 여러 entry로 나뉘면(`AVAILABLE −100` / `AVAILABLE +30` / `HOLD +70`) AVAILABLE이 from이면서 동시에 to가 되어 판정이 불가능하다. net 기준으로 바꾸면 `AVAILABLE −70`(from) / `HOLD +70`(to)로 정확히 1건의 전이가 된다 |
| **거래 균형 검증도 그룹 net 합** (`04 §8.12` `assertBalancedIfStatusMove`) | 동일 기준으로 통일 |
| **시리얼 SKU에 net 수량 검증 추가** (`04 §8.5`) | 개별 entry가 각각 `|1|`이어도 동일 시리얼이 2번 차감되면 net이 `−2`가 된다. `SERIAL_NET_QTY_INVALID` 신설 |
| **`hashStockKey` 구분자 명시** (`04 §8.12`) | 단순 문자열 결합은 `lotNo='AB'+serialNo='C'` 와 `'A'+'BC'` 가 충돌한다. 재고키 값에 등장할 수 없는 구분자(`\x1F`) 사용 |
| **`INSUFFICIENT_STOCK` 응답에 `entryCount`·`entryLineNos`** (`04 §8.6`, `05 §10.10`) | 사용자가 *"각 줄은 재고 범위 안인데 왜 실패하지?"* 라고 혼란스러워하는 것을 막는다 |
| **감사로그에 `groups` 요약 추가** (`04 §8.11`) | 사후에 "왜 통과/실패했는가"를 재구성하려면 합산 결과가 로그에 남아야 한다 |
| **`quantity_delta <> 0` CHECK의 적용 범위 명시** (`03 §6.4`) | **개별 entry 기준**이다. 그룹 net은 0일 수 있다(`−50`/`+50`) |
| **`lock_version` 증가 규칙 변경** (`03 §7`) | entry 수만큼이 아니라 **거래당 +1**(그룹 갱신 1회) |

# 3. REVERSAL 재취소 차단

## 3.1 지적 확인

v0.1은 `reversal_of_id` 조건부 UNIQUE로 **동일 거래의 재취소**만 막았다. **REVERSAL 거래 자체를 취소 대상으로 삼는 것**은 어느 조항도 금지하지 않아 `A → REV(A) → REV(REV(A)) → …` 체인이 가능했다. 신규 충돌 **C-14**로 등록했다.

## 3.2 반영 위치 (5중 방어)

| 층 | 구현 | 문서 |
|---|---|---|
| 1. **도메인** | `reverse()` 진입부에서 `original.transactionType === 'REVERSAL'` 검사 → `REVERSAL_OF_REVERSAL_NOT_ALLOWED` + `hint` | `04 §8.12` |
| 2. **Posting 검증** | 검증 ⑫에서 `reversalOfId` 대상의 `transactionType` 검사 | `04 §8.2`, `§8.12` |
| 3. **API** | `POST /api/inventory/transactions/{id}/reverse` → 422 + 오류코드 + 대안 안내. 응답에 `canReverse: boolean` | `05 §10.10` |
| 4. **화면** | 원장 목록·상세에서 `transactionType='REVERSAL'` 행에 **취소 버튼 미렌더링** + 툴팁 | `05 §11.12` |
| 5. **DB 트리거** | `trg_no_reversal_of_reversal` — `BEFORE INSERT` | `03 §6.4`, `04 §8.9` |

## 3.3 대안 안내

취소를 되돌려야 하면 **원인문서를 근거로 신규 정상거래를 생성**한다. 오류 메시지의 `hint`에 이 안내를 포함한다.

```
REVERSAL_OF_REVERSAL_NOT_ALLOWED
"취소 거래는 다시 취소할 수 없습니다."
hint: "취소를 되돌리려면 원인문서를 근거로 신규 정상거래를 생성하세요."
```

| **Q-07** | 3PL 대사 허용오차를 0이 아닌 값으로 둘 SKU | R1b 대사 운영 후 | 기본 0으로 시작 |
