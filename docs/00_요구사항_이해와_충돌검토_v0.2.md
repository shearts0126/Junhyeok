# 1. 요구사항 이해 요약

## 1.1 시스템이 해결하려는 핵심 문제

현재 DEEPPOINT의 SCM은 5개 엑셀/구글시트 43개 시트에 분산되어 있고, **재고의 단일 진실 원천(Single Source of Truth)이 존재하지 않는다.**

| # | 문제 | 실측 근거 |
|---|---|---|
| 1 | 현재고가 거래 집계가 아니라 조회 시트의 VLOOKUP 결과 | `재고현황!V8 = VLOOKUP('2. 현재고'!C:G,5,0)` — 3PL 스냅샷을 그대로 현재고로 사용 |
| 2 | 발주와 입고가 고유 ID가 아닌 **문자열 결합키**로 연결 | `발주현황!J5 = E5&F5&G5&H5&I5`, 이 키 **중복 13건** |
| 3 | 수불부가 월별 가로 확장 구조 | S&OP `올펀(포뷰트)` = **258열** (12개월 × 20열) |
| 4 | 재고 계산에 수기 보정이 상시 개입 | 월별 `그 외 조정 / 입고 조정 / 출고 조정` 3열 |
| 5 | 3PL별 상품코드·상품명이 내부 SKU와 다름 | 이벗매니저 상품명 **299/490건 공란** |
| 6 | 기획세트와 구성품 재고가 연결되지 않음 | 올리브영 기획세트 **6개 SKU 음수재고** (최대 −5,350) |
| 7 | 출고지시·실출고 대사가 수작업 | `출고 RAW` 15,667행 중 **매칭 실패 152건** |
| 8 | 발주잔량·입고지연을 육안 확인 | `입고현황 및 일정`에 *"입고 후 삭제"* 안내 — 이력 소실 |
| 9 | 재고 이력 미보존 | 위 + `_의 사본` 시트 3종 |
| 10 | 발주-입고 차이가 사후 확인만 가능 | 발주 477건 중 **차이 ≠ 0인 건 128건 (26.8%)** |

**본질적 해결책은 하나다.** 모든 재고 변동을 불변 거래원장에 원인문서와 함께 기록하고, 현재고를 그 집계 결과로만 산출한다.

## 1.6 재고 계산의 핵심 원칙

| # | 원칙 | 구현 |
|---|---|---|
| **P1** | 현재고는 원장 집계 결과 | `Σ quantity_delta WHERE business_date ≤ T` |
| **P2** | 현재고 직접 수정 불가 | 수정 API·화면 미제공. `InventoryPostingService`만 갱신 |
| **P3** | 확정 거래 물리삭제 금지 | 원장행 UPDATE/DELETE 트리거 차단 |
| **P4** | 취소·정정은 반대거래 | `REVERSAL`이 원거래 참조. 원거래 유지 |
| **P5** | 계획값은 재고를 변경하지 않음 | 출고예상·입고계획·발주잔량은 별도 테이블 |
| **P6** | 음수재고 원칙적 차단 | 잠금 후 검증. 예외는 5요건 충족 시만 |
| **P7** | 모든 거래는 원인문서를 가짐 | `OPENING_BALANCE` 외 필수 |
| **P8** | 외부 데이터는 한 번만 반영 | `idempotency_key` + 파일 해시 |
| **P9** | 상태 이동은 쌍으로 기록 | `AVAILABLE −100` + `HOLD +100` (합계 0) |
| **P10** | 원장 저장과 캐시 갱신은 하나의 트랜잭션 | 실패 시 전체 롤백 |
| **P11** | 수량은 `DECIMAL(18,6)` | float 금지 |
| **P12** | 시각은 UTC, 업무일자는 KST | `occurred_at` + `business_date` |
| **P13** | 3PL 재고는 원장을 덮어쓰지 않음 | 스냅샷 → 대사 → 승인된 조정 |
| ✏️ **P14** | **검증과 갱신은 재고키 단위로 합산** | 하나의 거래 안 동일 재고키 entry는 `netQuantityDelta`로 판정 |
| ✏️ **P15** | **취소의 취소는 금지** | `REVERSAL` 대상 취소 차단. 되돌리려면 신규 정상거래 |

# 2. 요구사항 충돌 및 누락 검토

## 2.1 문서 간 충돌 (Conflict)

| 구분 | 관련 문서·항목 | 문제 | 영향 | 권장 결정 | 상태 |
|---|---|---|---|---|---|
| **C-01** | Master PRD §11 vs 재고 PRD §5.3 | **가용재고 정의 충돌.** 차감식 vs 상태이동식 | 예약분 **이중 차감** → 가용재고 과소, 소진예상일 왜곡 | **재고 PRD 상태이동식 채택.** `가용재고 = AVAILABLE`. 화면 라벨을 `가용(AVAILABLE)`로 명시 | ✅ 승인 |
| **C-02** | Master PRD §7.2 vs 재고 PRD §4.2 | 창고이동 거래 단위 (4거래 vs 2트랜잭션×2행) | 진행상태 추적·취소 단위 상이 | **재고 PRD 채택.** `TRANSFER_DISPATCH` / `TRANSFER_RECEIPT` 각 1헤더 2행 | ✅ 승인 |
| **C-03** | 3개 PRD Release 1 정의 불일치 | 범위 3자 상충 | 일정·백로그 산정 불가 | ✏️ **합집합 + R1a-0~4 / R1b 재분할** (§1.3) | ✅ 승인·**v0.2 재분할** |

| **미확보 시 차선책** | 일 단위 집계 키(`올펀+창고+출고일+SKU+채널+목적`)로 하루 1건 반영. **건별 추적 포기**를 의미하므로 별도 승인 필요 |
| **문서 반영** | 06 v0.2 §12.10 · 07 v0.2 (R3 선결조건 명시) |

## D-05. 음수 기획세트 6건 — ✅ 확정

| | |
|---|---|
| **확정** | **① 실물 실사 → ② 과거 조립실적 소급 확인 → ③ 관리자 예외승인 순으로 처리한다. 0으로 임의 치환하지 않는다.** |
| **대상** | `FB-OY-SP-003`(−5,350), `FB-OY-ES-001`(−2,720), `FB-OY-CW-001`(−2,130), `FB-OY-TT-001`(−640), `FB-OY-SP-001`(−540), `FB-OY-TT-002`(−120) |
| **1단계 실사** | 오픈 전 올펀에 6개 세트 실물 실사 요청. 실사 수량을 오픈재고로 사용 |
| **2단계 조립소급** | 실사 불가 시, 과거 조립 실적을 확인해 `cutover_date` 이전 `ASSEMBLY_RECEIPT`/`ASSEMBLY_CONSUMPTION` 거래 생성으로 음수 해소 |
| **3단계 예외승인** | 위 둘 다 불가 시, **음수 그대로 `OPENING_BALANCE` 반영** + 재고 PRD §3.2 **예외 5요건 전부 충족**(관리자 권한·사유·승인 기록·예외큐 등록·해소 담당자와 기한) |
| **금지** | **0 치환 금지.** 마이그레이션 코드에 0 대체 분기를 두지 않는다 |
| **근본 원인** | 3PL이 구성품으로 세트를 조립·출고했으나 조립거래가 기록되지 않음. R3 세트조립 모듈 설계에 반영해 재발 방지 |
| **문서 반영** | 06 v0.2 §12.9 · 05 v0.2 §11.12(음수 라인 별도 탭) · 07 v0.2 T11-4 |

## D-06. 현재고에만 존재하는 SKU 4건 — ✅ 확정

| | |
|---|---|
| **확정** | **정식 SKU로 등록한다. `FB-SB`의 코드체계 위반은 ERROR가 아니라 WARNING + DataIssue로 관리한다.** |
| **대상** | `FB-DP-016`, `FB-PM-001`, `FB-PM-013`, `FB-SB` |

| **문서 반영** | 06 v0.2 §12.4·§12.11 · 03 v0.2 (검증 심각도) |

## D-07. 작성자·승인자 분리 — ✅ 확정

| | |
|---|---|
| **확정** | **SKU·BOM은 설정에 따라 자가승인을 허용할 수 있다. 재고조정·음수재고 예외·월마감 해제는 작성자와 승인자를 반드시 분리한다.** |
| **설정 가능 (자가승인 허용 가능)** | SKU 승인 / BOM 승인·활성화 / 바코드 중복 예외 / 외부매핑 / 공급조건 / 가격 승인 |
| **설정 불가 (항상 분리, 하드코딩)** | **① 재고조정 승인 ② 음수재고 예외 승인 ③ 월마감 해제** |
| **구현** | ✏️ **`system_setting.allow_self_approval_sku` / `allow_self_approval_bom`** (BOOLEAN, 기본 `false`) 두 설정으로 분리한다. 일반 `allow_self_approval` 컬럼은 만들지 않는다.<br>위 3종은 **설정값을 읽지 않고 코드에서 무조건 분리를 강제**한다 (`canSelfApprove()` 가 항상 `false`). **ADMIN 도 예외가 없다.** |
| **추가 통제** | 재고조정 관리자 추가승인·마감 해제는 **비밀번호 재인증** 필수 |
| **근거** | SKU·BOM은 잘못돼도 버전·상태로 되돌릴 수 있으나, 재고조정·마감해제는 회계·자산에 직결되고 사후 복구가 어렵다 |
| **문서 반영** | 03 v0.2 §7(`SystemSetting`) · 05 v0.2 §10.11·§10.14 · 07 v0.2 T01-4 |
