# 1. 요구사항 이해 요약

## 1.1 시스템이 해결하려는 핵심 문제

현재 DEEPPOINT의 SCM은 5개 엑셀/구글시트 43개 시트에 분산되어 있고, **재고의 단일 진실 원천(Single Source of Truth)이 존재하지 않는다.** 실측으로 확인한 구조적 문제는 다음과 같다.

| # | 문제 | 실측 근거 |
|---|---|---|
| 1 | 현재고가 거래 집계가 아니라 여러 조회 시트의 VLOOKUP 결과 | `재고현황!V8 = VLOOKUP(E8,'2. 현재고'!C:G,5,0)` — 3PL 스냅샷을 그대로 현재고로 사용 |
| 2 | 발주와 입고가 고유 ID가 아닌 **문자열 결합키**로 연결 | `발주현황!J5 = E5&F5&G5&H5&I5` (상품명+매입처+구분+차수+상세항목), 이 키 **중복 13건** |
| 3 | 수불부가 월별 가로 확장 구조 | S&OP `올펀(포뷰트)` 시트 = **258열** (12개월 × 20열) |
| 4 | 재고 계산에 수기 보정이 상시 개입 | 월별 `그 외 조정 / 입고 조정 / 출고 조정` 3개 열이 채널 합계와 동일 레벨에서 가감 |
| 5 | 3PL별 상품코드·상품명이 내부 SKU와 다름 | 이벗매니저/품고/로딧/쉽너지 4종 외부 상품명 병존, 이벗 상품명 **299/490건 공란** |
| 6 | 기획세트와 구성품 재고가 연결되지 않음 | 올리브영 기획세트 **6개 SKU 음수재고** (최대 −5,350) = 조립거래 누락 |
| 7 | 출고지시·실출고 대사가 수작업 | `출고 RAW` 15,667행 중 **SKU 매칭 실패 152건**이 `#N/A` 수식 결과로만 표시 |
| 8 | 발주잔량·입고지연을 담당자가 육안 확인 | `입고현황 및 일정` 시트에 *"입고 후 삭제"* 운영 안내 — 이력 소실 |
| 9 | 재고 이력이 보존되지 않음 | 위 삭제 운영 + `_의 사본` 시트 3종 (버전관리 부재) |
| 10 | 발주-입고 수량 차이가 사후 확인만 가능 | 발주 477건 중 **차이 ≠ 0인 건 128건 (26.8%)** |

**시스템의 본질적 해결책**은 단 하나다. **모든 재고 변동을 불변 거래원장(immutable ledger)에 원인문서와 함께 기록하고, 현재고를 그 집계 결과로만 산출한다.** 나머지 기능(발주, 입고, 출고, S&OP)은 모두 이 원장에 거래를 공급하거나 원장을 조회하는 주변부다.

## 1.2 주요 사용자

| 사용자 | 핵심 업무 | Release 1에서의 주 사용 화면 |
|---|---|---|
| **시스템 관리자** | 사용자·권한·공통코드, 마감 해제, 마이그레이션 실행, 연동 오류 처리 | 사용자관리, 공통코드, 월마감, 데이터이슈, 감사로그 |

| **3PL 사용자** | *(Release 1 계정 미발급)* | — |

> **권장 결정**: Release 1에서 3PL 사용자 계정은 발급하지 않는다. 3PL 데이터는 담당자가 파일 업로드로 취합한다. 근거 — Master PRD §6.6은 "직접 계정을 제공하는 경우"라는 조건부 서술이고, 재고 PRD §3.7은 3PL이 API/SFTP/CSV/엑셀 중 하나로 데이터를 "제공"한다고만 가정한다. 외부 계정은 권한·감사 표면적을 크게 넓히므로 Release 4로 미룬다.

## 1.5 시스템의 기준 데이터

기준 데이터는 두 층으로 구분한다.

### 층 1 — 마스터 (사람이 등록·승인하는 원천)

| 마스터 | 단일 원천 | 비고 |
|---|---|---|
| **SKU** | `sku` 테이블 | 엑셀 `최종 SKU MASTER` 490건이 유일 이관 원천. `SKU MASTER_본품`/`_부자재 등` 시트의 코드체계 표는 **공통코드 마스터**로만 이관 |
| 바코드 | `sku_barcode` | SKU 1:N |
| 외부 상품 매핑 | `sku_external_mapping` | 이카운트/이벗매니저/올펀/품고/로딧/쉽너지/채널 |
| 공통코드 | `common_code` 계열 | 브랜드 2, 대분류 13, 소분류 19, 부자재분류 39, 보관처 11 ✏️ *(v0.1 집계 오기 — 실측은 대분류 12·부자재분류 38·합계 98. 01_AS-IS §1.6 정오 참조)* |
| 거래처 | `supplier` | 지급조건 시트 40개사 + 거래처 정보 시트 |
| 공급조건 | `supplier_sku`, `supplier_sku_price` | BOM 시트에서 분리 |
| BOM | `bom_header`, `bom_line` | 버전·적용기간 필수 |
| 창고 | `warehouse`, `warehouse_location` | 3PL·제조사 보관처 포함 |

### 층 2 — 원장 (시스템이 생성하는, 재고의 단일 진실 원천)

| 원장 | 역할 |
|---|---|
| **`inventory_transaction`** | 업무 사건 1건 = 헤더 1행. 원인문서·멱등키·취소관계를 보유 |
| **`inventory_ledger_entry`** | 실제 재고 증감 1건 = 원장행 1행. **불변(INSERT only)** |
| `inventory_balance` | 조회 성능용 **캐시**. 원본이 아니며 원장에서 언제든 재구축 가능 |

> **핵심**: `inventory_balance`는 기준 데이터가 **아니다**. 원장이 기준이고 balance는 파생이다. 3PL이 제공하는 현재고 역시 기준이 아니라 **대사 대상**이다.

## 1.6 재고 계산의 핵심 원칙

| # | 원칙 | 구현 방식 |
|---|---|---|
| **P1** | 현재고는 원장 집계 결과다 | `현재고(재고키, T) = Σ quantity_delta WHERE occurred_at ≤ T` |
| **P2** | 현재고를 직접 수정할 수 없다 | 현재고 UPDATE API·화면 미제공. `inventory_balance`는 `InventoryPostingService`만 갱신 |
| **P3** | 확정 거래는 물리 삭제하지 않는다 | 원장행 UPDATE/DELETE 금지. DB 레벨 트리거로 차단 |
| **P4** | 취소·정정은 반대거래로 처리한다 | `REVERSAL` 거래가 원거래를 참조하며 반대 부호 원장행 생성. 원거래는 그대로 남음 |
| **P5** | 계획값은 재고를 변경하지 않는다 | 출고예상·입고계획·발주잔량·수요예측은 별도 테이블. 원장에 절대 반영 안 함 |
| **P6** | 음수재고는 원칙적으로 차단한다 | Posting 시 잠금 후 사전 검증. 예외는 권한+사유+승인+예외큐+해소추적 5요건 충족 시만 |
| **P7** | 모든 원장거래는 원인문서를 갖는다 | `OPENING_BALANCE` 외에는 `source_document_type/id` 필수 |
| **P8** | 외부 데이터는 한 번만 반영된다 | `idempotency_key` 조건부 UNIQUE + 파일 해시 |
| **P9** | 상태 이동은 쌍(pair)으로 기록한다 | `STATUS_CHANGE`: `AVAILABLE −100` + `HOLD +100` (합계 0) |
| **P10** | 원장 저장과 캐시 갱신은 하나의 트랜잭션이다 | 실패 시 전체 롤백. 부분 저장 불가 |
| **P11** | 수량은 `DECIMAL(18,6)`, 절대 float 아님 | BOM 소요량 1/30 같은 분수 필요 |
| **P12** | 시각은 UTC 저장, 업무일자는 KST 기준 | `occurred_at TIMESTAMPTZ` + `business_date DATE` (KST 파생, 인덱스용) |
| **P13** | 3PL 재고는 원장을 덮어쓰지 않는다 | 스냅샷 저장 → 대사 → 원인 규명 → 승인된 조정거래로만 반영 |

# 2. 요구사항 충돌 및 누락 검토

> **판정 기준**: 지시하신 우선순위(① 세부 PRD → ② Master PRD → ③ 엑셀 운영방식 → ④ 일반 관행)를 적용했다.
> **차단** = 이 결정 없이는 해당 모듈 구현 착수 불가.

## 2.1 문서 간 충돌 (Conflict)

| **G-08** | 재고 PRD §22 전체 | **`business_date`(업무일자) 개념이 컬럼으로 없다.** `occurred_at TIMESTAMPTZ`(UTC)만 존재하는데 §4.5는 "업무일자는 Asia/Seoul 기준" | 일별 수불부·마감 경계가 UTC 자정으로 잘려 **KST 09:00 이전 거래가 전날로 집계**됨. 월마감도 어긋남 | `inventory_ledger_entry`와 `inventory_transaction`에 **`business_date DATE NOT NULL`** 을 추가하고 `(occurred_at AT TIME ZONE 'Asia/Seoul')::date`로 산출·저장한다(생성 컬럼 또는 서비스 계산). 일별·월별 집계와 마감 판정은 **전부 `business_date` 기준**. `occurred_at`은 순서·감사용 |
| **G-09** | 재고 PRD §11.3 "거래 후 잔량" | 원장행에 잔량을 저장하면 동시성 하에서 정확한 값을 보장하려면 재고키 단위 직렬화가 필요. PRD는 "필수 저장값으로 사용하지 않아도 된다"고만 함 | 저장하면 성능·정합성 리스크, 안 하면 화면 요구 미충족 | **저장하지 않고 조회 시 계산**한다. `SUM(quantity_delta) OVER (PARTITION BY 재고키 ORDER BY business_date, occurred_at, transaction_id, line_no ROWS UNBOUNDED PRECEDING)`. 정렬 결정성을 위해 `id`까지 tie-breaker에 포함 |
| **G-10** | SKU·BOM PRD §21 공용 부자재 | 보관처 축약코드 방식(`FB-CM-002-CLB`)의 **처리 방침이 3개 선택지로 열려 있음**(외부매핑 / 소유위치 / 별도 SKU). 실측: `부자재 현황` 시트가 보관처별로 재고를 **실제 분리 관리** 중 | 선택에 따라 SKU 수·BOM 라인·재고키가 전부 달라짐 | **`부자재 현황` 실측을 근거로 "별도 SKU 유지 + 제조사 창고" 하이브리드 채택.** ① 엑셀에 이미 존재하는 `-CLB` 등 접미 SKU는 **코드 그대로 이전**(§11.1 "임의 재생성 금지"). ② 동시에 제조사를 `warehouse_type = SUPPLIER_SITE` 창고로 등록해 **재고 위치로도 구분**. ③ BOM 라인은 접미 없는 **공용 SKU(`FB-CM-002`)를 구성품으로 연결**(§21 원칙), 접미 SKU는 `bom_line.legacy_common_bom_code`에 참고 보관. ④ 장기적으로 접미 SKU를 창고 차원으로 흡수하는 정리 과제를 백로그에 남김 |
| **G-11** | 세 PRD 전체 | **작성자 = 승인자 허용 여부**가 "설정값으로 관리하되 기본은 분리"(SKU·BOM PRD §34)로만 서술. 실제 SCM 인원이 소수이면 업무가 멈춤 | 승인 대기 교착 | `system_setting.allow_self_approval` (기본 `false`)를 도입하고, **엔티티 유형별로 override 가능**하게 설계. 단 **재고조정·음수재고 예외·월마감 해제는 override 불가(항상 분리)** 로 고정한다 |
| **G-12** | 재고 PRD §19.6 허용오차 | "기본값 0, SKU별 별도 설정 가능"인데 **설정 테이블이 정의되지 않음** | 대사 화면에서 오차 설정 불가 | `sku.reconciliation_tolerance_qty DECIMAL(18,6) NOT NULL DEFAULT 0` 컬럼으로 SKU에 직접 보유. 별도 테이블 불필요 |

> ✏️ **2026-08-25 설계복구 (Warehouse, T08)**: **G-05** 의 결정 자체(창고 생성 트랜잭션 안에서 `DEFAULT` 로케이션을 자동 생성하고 `default_location_id` 를 **NOT NULL** 로 강제한다)는 정본으로 유지된다. 다만 괄호 안의 **"생성 후 즉시 UPDATE"** 는 `CLARIFIED BY 19_설계복구_Warehouse.md §W-D7·§W-D8` 이다 — `default_location_id` 가 NOT NULL 이면 "창고를 먼저 INSERT 하고 나중에 UPDATE" 라는 순서 자체가 성립하지 않는다(첫 INSERT 가 NOT NULL 을 위반한다). 실제 순서는 **① location `id`(UUID)를 애플리케이션에서 미리 생성 → ② `warehouse` INSERT 시 `default_location_id` 에 그 UUID 를 채워 넣음 → ③ `warehouse_location` INSERT(`location_code='DEFAULT'`) → ④ COMMIT 시점에 deferred FK 검증** 이며, **별도 UPDATE 문은 없다**. `DEFERRABLE INITIALLY DEFERRED` 는 ②↔③ 의 순환 참조를 커밋 시점까지 미루기 위한 것이고, 이 FK 는 **같은 창고의 로케이션만 가리키도록 composite FK** 로 건다(**§W-D6**). `DEFAULT` 는 예약 코드이며 사용자가 만들거나 바꿀 수 없다(**§W-D9·§W-D10**).

## 2.3 엑셀 운영방식 ↔ 원장 방식 충돌 (Legacy)

| 구분 | 엑셀 운영방식 | 신규 원장 방식 | 권장 결정 |
|---|---|---|---|
| **L-01** | `입고현황 및 일정` 시트: *"입고 후 삭제"* | 확정 데이터 물리삭제 금지 | 입고 완료 시 `status = COMPLETED` 전환 + 기본 필터에서 숨김. **삭제 UI 자체를 제공하지 않는다.** 담당자에게는 "완료 필터"로 동일한 화면 경험 제공 |
| **L-02** | 월별 `그 외 조정 / 입고 조정 / 출고 조정` 열로 수기 보정 | 조정은 승인된 `MANUAL_ADJUSTMENT` 거래로만 | 과거 조정값은 **원장으로 전환하지 않는다**(재고 PRD §25.1). 참조용 `legacy_sop_plan` 테이블에 원본 보관. 신규 조정은 사유코드·증빙·승인 필수 |
| **L-03** | 현재고 = 3PL(`2. 현재고`) VLOOKUP 결과 | 3PL은 대사 대상, 원장이 기준 | 전환 기준일 3PL 현재고를 **`OPENING_BALANCE`로 1회 확정**한 뒤, 이후 3PL 수치는 `external_inventory_snapshot`으로만 수집. 자동 덮어쓰기 경로를 코드상 아예 만들지 않음 |
| **L-04** | 발주-입고 연결키 = 문자열 결합(`구분2`) | 안정적 고유 ID | 이관 시 `legacy_join_key` 컬럼에 원문 보존 + 신규 `purchase_order_line_id` 부여. **중복 13건은 담당자 수동 판정 대상**으로 마이그레이션 이슈 등록 |
| **L-05** | S&OP 시트에 계획(출고예상·입고계획)과 실적(실출고·실입고)이 같은 표에 혼재 | 계획과 실적 완전 분리 | 계획은 `legacy_sop_plan`(참조) → R5에서 `demand_forecast`/`inbound_plan`으로 정식화. 실적은 기준일 이전은 이관하지 않고 기초재고로 대체 |
| **L-06** | 부자재 잔량 = `부자재 입고 − 본품 발주 + 조정` (SUMIF에 품번 하드코딩) | 제조사 보관 재고도 원장으로 | R1은 제조사 창고(`SUPPLIER_SITE`)와 기초재고만 세팅. 소요 차감은 R2 발주·사급출고 모듈에서 정식 거래로 대체. **엑셀 수식을 이식하지 않는다** |
| **L-07** | 바코드가 숫자로 저장되어 지수표기 발생 | 문자열 저장 필수 | 파싱 시 셀을 **문자열로 강제 읽기**, `1.23E+12` 패턴 탐지 시 **행 전체를 오류 처리**(복원 시도 금지 — 유효자릿수 손실은 복구 불가). 실측상 원본 xlsx는 정수 보존 상태이나 CSV 경유 시 위험 |

| **영향** | ⓐ: 오픈이 빠르고 실사 부담이 작음. 단 유통기한 임박 관리(Master PRD DOC-10)는 전환 후에야 가능. ⓒ: 오픈 전 전 SKU LOT 실사 필요 — 3PL 협조 없이는 비현실적 |
| **차단** | ✅ **기초재고 양식 확정 차단** |

## D-04. 3PL(올펀) 출고 원본에서 출고번호·라인ID를 확보할 수 있는가

| | |
|---|---|
| **질문** | 올펀에서 출고 건별 고유번호(출고번호 또는 주문번호 + 라인번호)를 받을 수 있는가? |
| **선택지** | ⓐ 확보 가능 — 건별 원장 반영, 완전한 멱등성 <br> ⓑ 확보 불가 — 일 단위 집계 키로 반영(건별 추적 포기) <br> ⓒ 미정 — R1에서는 출고 원장 반영 자체를 하지 않음 |
| **권장안** | **R1은 ⓒ로 진행하되, 즉시 올펀에 ⓐ를 요청**한다. 근거: R1은 기준일 현재고 방식이므로 과거 출고를 원장에 넣을 필요가 없다. 그러나 R3/R4 출고 연동은 ⓐ 없이는 **재업로드 시 이중 차감을 구조적으로 막을 수 없다.** ⓑ는 "어느 주문의 출고인지" 추적을 영구히 포기하는 것이라 출고대사(Master PRD 1차 목표)가 반쪽이 됨 |
| **영향** | ⓐ 불가 시 Master PRD 성공지표 "출고대사 시간 80% 감소"의 달성 수준이 낮아짐. 계약·협의 리드타임이 필요하므로 **지금 착수해야 R3에 늦지 않음** |
| **차단** | ❌ R1 비차단 / ✅ **R3 출고 연동 차단** |

## D-05. 음수 기획세트 6건을 어떻게 해소할 것인가

| | |
|---|---|
| **질문** | `FB-OY-CW-001`(−2,130), `FB-OY-ES-001`(−2,720), `FB-OY-SP-001`(−540), `FB-OY-TT-001`(−640), `FB-OY-TT-002`(−120), `FB-OY-SP-003`(−5,350) 을 오픈재고로 어떻게 넣는가? |
| **선택지** | ⓐ 조립 실적을 소급 확인해 기준일 이전 조립거래로 해소 후 정상 오픈 <br> ⓑ 음수 그대로 `OPENING_BALANCE` + 관리자 승인 예외 + 예외큐 등록 <br> ⓒ 실사로 실물 확인 후 실사 결과를 오픈재고로 사용 |
| **권장안** | **ⓒ → ⓐ → ⓑ 순.** 오픈 전 올펀에 해당 6개 세트의 **실물 실사**를 요청하는 것이 가장 정확하다(6종뿐이므로 실현 가능). 실사가 불가하면 조립 실적 소급(ⓐ), 그것도 불가하면 예외 승인(ⓑ). **0으로 치환은 어떤 경우에도 금지**(재고 PRD §26.3) |

| **차단** | ✅ **기초재고 승인 차단** |

## D-06. 미등록 SKU 4건과 코드체계 위반을 어떻게 처리할 것인가

| | |
|---|---|
| **질문** | 현재고에 존재하나 SKU MASTER에 없는 `FB-DP-016`, `FB-PM-001`, `FB-PM-013`, `FB-SB`를 어떻게 하는가? (`FB-SB`는 3세그먼트로 코드체계 위반) |
