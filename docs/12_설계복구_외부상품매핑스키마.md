두 지점이 자체적으로 해소 불가능해 `T05-1 PRE-FLIGHT BLOCKED` 로 보고했다.

## 2. Warehouse dependency

`Warehouse` / `WarehouseLocation` 은 **T08-1** 의 범위다 (`07_개발백로그와_테스트전략.md:109`).
T05-1 에서 `Warehouse` 모델을 만드는 것은 다른 Epic 의 선구현이므로 금지한다.

동시에 `warehouseId` 필드 자체는 surviving 모델 선언에 명시되어 있으므로 **삭제하지 않는다.**
컬럼과 관계를 시점 분리한다.

```text
column now  →  T05-1
relation/FK later  →  T08-1
```

### warehouseId staged scalar decision (확정 = Option A)

T05-1 에서 만드는 것:

```prisma
/// T05-1 Design Recovery:
/// scalar 컬럼만 유지한다. Warehouse FK/relation 은 T08-1 로 미룬다.
warehouseId String? @map("warehouse_id") @db.Uuid
```

DB 상태:

```text
warehouse_id UUID NULL
FK 없음
```

T05-1 에서 만들지 않는 것:

```text
Warehouse model
WarehouseLocation model
SkuExternalMapping.warehouse relation
Warehouse.externalMappings inverse relation
warehouse_id FK 제약
```

따라서 현재는 **임의 UUID 를 `warehouse_id` 에 저장해도 FK 위반이 나지 않는다.**
이는 사고가 아니라 의도된 staged state 이며, DB 테스트로 고정했다
(`tests/db/sku-external-mapping-schema.test.ts` — `warehouse FK deferred to T08-1` 주석).

### T08-1 후속 의존사항 (필수)

T08-1 에서 `Warehouse` 를 구현할 때 **반드시 함께** 추가한다.

```text
SkuExternalMapping.warehouse   (optional relation)
Warehouse.externalMappings     (inverse)
warehouse_id FK 제약
```

예상 방향은 다음과 같다. 단 T08-1 실제 구현 직전에 그 시점의 repo·설계를 다시 검토한다.

```text
nullable warehouseId → optional Warehouse relation → onDelete Restrict → onUpdate Cascade
```

⛔ **T05-1 에서 미래 FK migration 을 미리 만들어 두지 않는다.**
⛔ T08-1 에서는 위 DB 테스트가 **반대 방향으로 바뀌어야 한다**(임의 UUID → FK 위반).

> ✏️ **2026-08-25 설계복구 (Warehouse, T08)**: 위 후속 의존사항은 **`19_설계복구_Warehouse.md §W-D15` 가 인수**했다 — `SkuExternalMapping.warehouseId` 는 T08-1(= v0.2 `T2-1A`)에서 **staged scalar → real FK/relation 으로 landing 되는 5종 중 #1** 이다(나머지: `Supplier.defaultWarehouseId`·`SupplierSku.destinationWarehouseId`·`BomHeader.destinationWarehouseId`·`BomLine.issueWarehouseId`). 위 "예상 방향"(`onDelete: Restrict` · `onUpdate: Cascade`)은 **§W-D19 FK matrix 가 그대로 확정**했고, inverse relation 이름은 **§W-D16** 이 정한다. 위 마지막 줄대로 **`tests/db/sku-external-mapping-schema.test.ts` 의 "임의 UUID 저장 가능" 테스트는 T08-1 에서 FK 위반 방향으로 뒤집는다**(**§W-D21** — 기존 staged-state 테스트의 supersession 목록에 포함).

## 3. ExternalInventorySnapshot dependency

`ExternalInventorySnapshot` / `…Line` 은 **T17-1** 이고, T17-1 의 선행조건이
`T05-1, T08-1` 이다 (`07:218`). T05-1 에서 stub 모델을 먼저 만들면 의존이 역전된다.
Prisma 는 relation 의 양쪽 모델이 모두 존재해야 하므로 `snapshots` 만 선언할 수도 없다.

### snapshots relation — T17-1 deferred


이는 원 설계의 폐기가 아니라 **의존순서에 맞춘 staged implementation** 이다.

```text
ExternalSystem.snapshots
ExternalInventorySnapshot.externalSystem
```

본 PR 에서 `ExternalInventorySnapshot` · `ExternalInventorySnapshotLine` 이
production Prisma model 로 생기지 않았음을 DB 테스트로 고정했다.

## 4. model-specific fields 우선

원 설계 안에서도 **모델 선언**과 **일반 규약/ERD 요약**이 어긋난다. 본 결정은
T04-1 에서 적용한 원칙을 그대로 재사용한다.

```text
model-specific authoritative schema  >  generic convention
```

### audit-column conflict resolution

`03 §공통 규약:18` 은 `created_at / created_by / updated_at / updated_by` 4종을 말한다.
그러나 surviving 모델 선언은:

| 모델 | 선언된 감사 컬럼 |
|---|---|
| `SkuExternalMapping` | `createdAt` **만** |
| `ExternalSystem` | **없음** |

확정:

- `SkuExternalMapping` 은 `createdAt` 만 가진다.
  추가 금지 — `createdBy` · `updatedAt` · `updatedBy` · `deletedAt`.
- `ExternalSystem` 은 timestamp 컬럼 자체를 두지 않는다.
  추가 금지 — `createdAt` · `createdBy` · `updatedAt` · `updatedBy` · `deletedAt`.

일반 ERD 규약과 충돌하지만 본 Recovery Decision 으로 잠근다. 향후 실제 업무상
감사가 필요하면 Application `AuditLog` 에서 별도로 처리한다. **T05-1 은 API 자체가
없으므로 AuditLog 도 없다.**

### 타입 관련 확정

- `systemName` — Prisma `String` 그대로. PostgreSQL **TEXT**.
  ⛔ 임의 `@db.VarChar(...)` 금지.
- `systemType` — `String @db.VarChar(30)` 유지.
  ⛔ `ExternalSystemType` / `ERP·WMS·THREE_PL·CHANNEL` enum 금지.
  주석의 값들은 **예시**이지 authoritative enum 이 아니다.
- `MappingStatus` — 정확히 3값 (`MATCHED` `UNMATCHED` `REVIEW_REQUIRED`).
  ⛔ 값 추가 금지. DB CHECK·String 으로 대체하지 않고 현재 repo 의 Prisma enum
  convention (`SkuStatus` · `BarcodeType`) 을 따른다.

### 컬럼명 매핑 (구현 세부)

원 문서의 Prisma 선언에는 `@map` 이 없지만, 본 repo 는 전 테이블이 snake_case
컬럼이며(`20260806090000_rename_auth_columns_to_snake_case`) 무엇보다 §5 의
authoritative raw SQL predicate 가 `external_system_id` · `external_product_code` ·
`effective_to` · `is_primary` · `sku_id` 를 **snake_case 로 명시**한다.
따라서 `@map` 을 붙여 물리 컬럼명을 원문 SQL 과 일치시킨다.
이는 필드 추가·변경이 아니라 기존 repo convention 으로의 정합이다.

## 5. partial UNIQUE exact predicates

`03 §고유조건·인덱스:287` 의 `sku_external_mapping` 행이 authoritative 다.
모델 주석에는 1종만 적혀 있으나 §고유조건에는 **2종**이 있으며, 2종 모두 만든다.
두 규칙은 **서로 다른 규칙**이므로 하나의 composite unique 로 합치지 않는다.

### `ux_external_mapping_code`

```sql
CREATE UNIQUE INDEX "ux_external_mapping_code"
ON "sku_external_mapping" ("external_system_id", "external_product_code")
WHERE "external_product_code" <> ''
  AND "effective_to" IS NULL;
```

⛔ `external_product_code IS NOT NULL` 을 **추가하지 않는다.**
PostgreSQL 에서 `NULL <> ''` 는 `NULL` 이고 partial index 는 predicate 가 TRUE 인
행만 담으므로 NULL 은 이미 제외된다. authoritative predicate 를 불필요하게
재작성하지 않는다.

### `ux_external_mapping_primary`

```sql
CREATE UNIQUE INDEX "ux_external_mapping_primary"
ON "sku_external_mapping" ("sku_id", "external_system_id")
WHERE "is_primary" = true;
```

⛔ `AND effective_to IS NULL` 을 **추가하지 않는다.** 문서에 없다.
⛔ `sku_barcode` 의 primary predicate(`AND status='ACTIVE'`)를 복사하지 않는다.

### index 이름

문서에 이름이 없어 본 결정에서 확정한다 — 정확히
`ux_external_mapping_code` · `ux_external_mapping_primary`.

### 왜 DB 카탈로그 테스트가 필수인가

`prisma migrate diff` 는 partial index 를 **보지 못한다**(T04-1·T04-4A 실측).
raw SQL 을 빼먹어도 drift gate 는 통과한다. 따라서 PostgreSQL 카탈로그
(`pg_index.indpred` / `pg_get_expr`) 를 직접 조회하는 테스트가 유일한 방어선이다.
predicate 문자열까지 정확히 고정하며, 특히 primary predicate 에 `effective_to` 가
**없음**을 명시적으로 테스트한다.

## 6. empty/null external code semantics

`externalProductCode` 는 NULL 과 빈 문자열이 **모두 schema level 에서 허용**된다.

| 값 | `ux_external_mapping_code` | 동일 system 내 다중 |
|---|---|---|
| `NULL` | predicate 가 NULL → 대상 아님 | ✅ 허용 |
| `''` | `<> ''` 가 false → 대상 아님 | ✅ 허용 |
| `'P001'` + `effectiveTo IS NULL` | 대상 | ❌ 중복 차단 |
| `'P001'` + `effectiveTo IS NOT NULL` | 대상 아님 | ✅ 이력으로 공존 |

⛔ 다음을 두지 않는다.

```text
NOT BLANK CHECK
trim CHECK
CHECK (external_product_code <> '')
```

빈 값을 금지하면 predicate 가 빈 문자열을 **명시적으로 제외 대상**으로 삼는
authoritative 설계와 모순된다. T05-2 의 DTO·정규화 계약과 DB storage 계약을 섞지 않는다.

## 7. primary UNIQUE semantics

현재 authoritative invariant 는 다음 한 줄이다.

```text
SKU × ExternalSystem 당 isPrimary=true 는 최대 1개
```

`effectiveTo` 와 **무관**하다. 따라서 종료된 과거 매핑이라도 `isPrimary=true` 로
남아 있으면 같은 (SKU, ExternalSystem) 의 새 대표를 막는다.
UX 상 불편해 보여도 **T05-1 스키마에서 고치지 않는다.**
매핑 종료·대표 변경 semantics 는 T05-2 에서 명시적으로 설계한다.

허용:


⛔ 추가 금지 (근거 없음):

## 11. TC-SKU-009 recovered DB acceptance

`TC-SKU-009` 는 백로그에 이름만 5회 등장하고 **상세 Given/When/Then 원문이 없다**
(`07:78`, `07:415`, `07_v0.2:85·102·532`). 본 Recovery Decision 에서 T05-1 의 DB
인수조건을 다음 6개로 고정한다.

### TC-SKU-009A — ExternalSystem identity

```text
Given  ExternalSystem systemCode='LEGACY_ERP' 가 존재
When   동일 systemCode 를 다시 INSERT
Then   DB unique violation
```

다른 `systemCode` 는 허용.

### TC-SKU-009B — current external code uniqueness

```text
Given  system A + externalProductCode='P001' + effectiveTo=NULL
When   동일 system A + 'P001' + effectiveTo=NULL 을 INSERT
Then   ux_external_mapping_code violation
```

### TC-SKU-009C — system isolation

```text
system A + 'P001'
system B + 'P001'
```

→ 둘 다 허용. ERP·WMS·3PL 별칭이 **시스템별로 분리**된다는 인수조건을 DB 차원에서 고정한다.

### TC-SKU-009D — historical mapping

```text
system A + 'P001' + effectiveTo != NULL
system A + 'P001' + effectiveTo  = NULL
```

→ 공존 허용.

### TC-SKU-009E — no-code mapping

동일 system 에서 `externalProductCode = NULL` 여러 건 허용.
동일 system 에서 `externalProductCode = ''` 여러 건 허용.

### TC-SKU-009F — primary

동일 `(skuId, externalSystemId)` 에서 `isPrimary=true` 2건 →
`ux_external_mapping_primary` violation. **`effectiveTo` 가 있어도 동일하다.**
`externalSystem` 이 다르면 각각 primary 1개씩 허용.
